# Предпроектная аналитика сервиса трекинга криптопортфеля

## 1. Проблема проекта и что будет решать

Для профессионального управления криптовалютным портфелем критически важно оценивать эффективность использования капитала с учётом рисков на основе институциональных метрик (коэффициенты Шарпа и Сортино, показатели VaR, MERC), а также отслеживать общие индикаторы рыночной капитализации в едином интерфейсе. Проверка каждого параметра и ручной расчёт матриц по разрозненным данным блокчейнов увеличивают затраты времени на анализ и затрудняют своевременное реагирование на рыночные изменения.

В связи с этим планируется разработка аналитического сервиса для отображения текущих показателей портфеля, оценки рисков и вывода истории изменений через веб-интерфейс (браузер). Предполагаемые пользователи — владельцы крупных частных портфелей, учебные команды и администраторы небольших инвестиционных компаний.

Также предусмотрена возможность централизованного или локального развертывания системы — запуск серверной части и клиентского веб-приложения из готовых Docker-образов на выделенных серверах, что обеспечивает полную изоляцию компонентов, масштабируемость системы и безопасное хранение данных внутри контролируемой инфраструктуры.

## 2. Что необходимо определить до разработки

До начала разработки требуется определить оптимальный подход к агрегации, расчёту и доставке исторических данных для институциональных финансовых метрик на стороне серверной инфраструктуры.

Существует 3 основных подхода:
- on-the-fly — расчёт показателей доходности и рисков «на лету» непосредственно в момент запроса пользователя;
- snapshots — ежесуточная фиксация слепков балансов и цен на сервере с заблаговременным вычислением исторических метрик;
- гибридный подход — фиксация балансов и цен закрытия в слепках на сервере бэкенда с последующим динамическим расчётом сложных метрик (MERC, ковариация активов) по запросу за выбранный период.

## 3. Сравнение способов получения данных

| Подход | Организация работы | Преимущества для проекта | Ограничения |
|---|---|---|---|
| **on-the-fly** | При запросе бэкенд на сервере собирает всю историю транзакций и цен, проводя вычисления в реальном времени. | Не требует хранения избыточных расчетных точек; показатели абсолютно точны на текущую секунду. | Высокая нагрузка на CPU сервера при матричных вычислениях (ковариация, VaR); долгий ответ при большой истории сделок. |
| **snapshots** | Сервер раз в сутки (в 23:59:59) фиксирует состояние портфелей и цен, сохраняя готовые агрегированные точки в БД. | Максимальная скорость загрузки графиков и метрик в интерфейсе; минимальная нагрузка на базу данных сервера. | Данные обновляются раз в день; изменения внутри текущего дня не учитываются в исторических коэффициентах до полуночи. |
| **Гибридный подход** | Исторические балансы и цены закрытия дней фиксируются в слепках на сервере, а финальные показатели считаются при запросе. | Оптимальный баланс между скоростью работы СУБД и возможностью динамически выбирать безрисковую ставку. | Требует проектирования составных индексов в БД во избежание просадок производительности при одновременных запросах. |

**Предварительный выбор:** гибридный подход наиболее точно соответствует сценарию построения институциональной аналитики по историческим периодам на выделенном сервере.

### 3.1. Подходы уже существующих решений

## 4. Предлагаемые требования к первой версии

| Компонент | Предлагаемые функции | Обоснование |
|---|---|---|
| **Аналитический модуль** | Расчет показателей доходности (Шарп, Сортино, FOMO), рисков (VaR через квантили, volatility drag, diversification ratio, ENA, MERC) и ковариаций. | Предоставление пользователю глубокой институциональной оценки портфеля и рисков. |
| **Сервер (Бэкенд)** | Прием транзакций, валидация данных, ежесуточное создание слепков, синхронизация цен с внешними API и сбор макро-индикаторов. | Централизованная обработка исторических, потоковых и рыночных данных. |
| **Фронтенд-приложение** | Интерактивный вывод списков портфелей, последних показателей, матриц корреляции, тепловых карт рисков и графиков макро-рынка. | Удобное визуальное отображение сложных математических метрик в одном месте. |
| **Хранение** | Сохранение времени измерения и времени приема, точная фиксация объемов монет, история транзакций, ежедневные слепки, справочник цен и ставок. | Обеспечение базы для исторических расчетов и исключение ошибок округления для блокчейн-активов в СУБД. |
| **Рыночный мониторинг** | Сбор внешних метрик капитализации рынка: Open Interest, Fear & Greed index, capital flow, BTC/ETH hashrate. | Оценка общего состояния рынка криптовалют при анализе личного портфеля. |
| **Управление рисками** | Возможность выбора и переключения безрисковой ставки пользователем для пересчета коэффициентов. | Адаптация расчетов под разные варианты (гособлигации США или стейблкоин-лендинг). |
| **Установка инфраструктуры** | Готовые образы для бэкенда и фронтенда, Compose-файл, пример настроек и инструкция. | Самостоятельное развертывание всех компонентов сервиса на целевых серверах. |

## 5. Самостоятельное развёртывание

Предлагаемая схема: **внешние крипто-API -> серверное API (Бэкенд) -> база данных**. Фронтенд-приложение запрашивает и получает данные через API.

| Способ установки | Что потребуется от администратора | Особенности |
|---|---|---|
| Ручная установка | Установить на серверах среды выполнения для бэкенда и фронтенда, зависимости, СУБД и настроить планировщик. | Позволяет управлять компонентами отдельно, но требует ручной настройки их совместимости. |
| Готовые контейнерные образы | Подготовить контейнерную среду на серверах, заполнить настройки в `.env` и запустить Compose. | Минимизирует порог входа, но требует поддержки актуальности образов и порядка обновления. |

В качестве основного метода развёртывания выбраны готовые контейнерные образы для серверных сред. В комплект поставки входят: docker-compose файлы для одновременного поднятия контейнеров фронтенда и бэкенда, примеры env-файлов с конфигурацией портов и API-ключей, а также инструкция для запуска.

Фронтенд-приложение, бэкенд, база данных и вычислительный модуль устанавливаются и изолируются непосредственно на выделенных серверных мощностях. Взаимодействие бэкенда со сторонними крипто-API вынесено в отдельные асинхронные воркеры.

## 6. Вывод

Для разрабатываемого сервиса будет использоваться гибридный подход с ежедневным логированием состояний активов и цен на сервере (подход snapshots для хранения данных и on-the-fly для расчета коэффициентов). Данный выбор позволит без задержек просматривать сложные институциональные показатели доходности и рисков через единый интерфейс клиентского приложения. При этом использование изолированного справочника безрисковых ставок предоставит возможность кастомизировать расчеты под требуемые рыночные условия.

Компоненты системы — серверное API (бэкенд) и клиентское веб-приложение (фронтенд) — будут доступны в виде готовых контейнерных образов. Развертывание всей инфраструктуры на выделенных серверах осуществляется с помощью Docker Compose на основе параметров среды, указанных в инструкции к файлу `.env`. Использование готовых образов избавляет от необходимости ручной сборки зависимостей приложения и изолированного поднятия базы данных, обеспечивая при этом стабильную серверную производительность, независимое масштабирование слоев и безопасность данных.
