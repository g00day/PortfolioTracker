# Предпроектная аналитика сервиса трекинга криптопортфеля

## 1. Проблема проекта и что будет решать

Для профессионального управления криптовалютным портфелем критически важно оценивать эффективность использования капитала с учётом рисков на основе институциональных метрик (коэффициенты Шарпа и Сортино, показатели VaR, MERC), а также отслеживать общие индикаторы рыночной капитализации в едином интерфейсе. Проверка каждого параметра и ручной расчёт матриц по разрозненным данным блокчейнов увеличивают затраты времени на анализ и затрудняют своевременное реагирование на рыночные изменения.

В связи с этим планируется разработка аналитического сервиса для отображения текущих показателей портфеля, оценки рисков и вывода истории изменений через веб-интерфейс. Предполагаемые пользователи — владельцы крупных портфелей, учебные команды и администраторы небольших инвестиционных компаний.

Также предусмотрена возможность самостоятельного развертывания системы — запуск собственного экземпляра сервиса из готовых Docker-образов для хранения данных внутри изолированной инфраструктуры пользователя, что обеспечивает полную конфиденциальность балансов.

## 2. Что необходимо определить до разработки

До начала разработки требуется определить оптимальный подход к агрегации и расчёту исторических данных для институциональных финансовых метрик.

Существует 3 основных подхода:
- on-the-fly — расчёт показателей доходности и рисков «на лету» непосредственно в момент запроса пользователя;
- snapshots — ежесуточная фиксация слепков балансов и цен с заблаговременным вычислением исторических метрик;
- гибридный подход — фиксация балансов и цен закрытия в слепках с последующим динамическим расчётом сложных метрик (MERC, ковариация активов) по запросу за выбранный период.

## 3. Сравнение способов получения данных

| Подход | Организация работы | Преимущества для проекта | Ограничения |
|---|---|---|---|
| **on-the-fly** | При запросе бэкенд собирает всю историю транзакций и цен, проводя вычисления в реальном времени. | Не требует хранения избыточных расчетных точек; показатели абсолютно точны на текущую секунду. | Высокая нагрузка на CPU при матричных вычислениях (ковариация, VaR); долгий ответ при большой истории сделок. |
| **snapshots** | Сервер раз в сутки (в 23:59:59) в фоновом режиме фиксирует состояние портфелей и цен, сохраняя готовые агрегированные точки. | Максимальная скорость загрузки графиков и метрик в интерфейсе; минимальная нагрузка на базу данных. | Данные обновляются раз в день; изменения внутри текущего дня не учитываются в исторических коэффициентах до полуночи. |
| **Гибридный подход** | Исторические балансы и цены закрытия дней фиксируются в слепках, а финальные показатели считаются при запросе. | Оптимальный баланс между скоростью работы СУБД и возможностью динамически выбирать безрисковую ставку. | Требует проектирования составных индексов для таблиц слепков и котировок во избежание просадок производительности. |

**Предварительный выбор:** гибридный подход наиболее точно соответствует сценарию построения институциональной аналитики по историческим периодам.

### 3.1. Подходы уже существующих решений

| Решение | Что подтверждает документация | Значение для проекта |
|---|---|---|
| CoinGecko Portfolio | Использует snapshot-модель для отображения исторических графиков баланса. | Подтверждает необходимость фиксации ежедневных срезов цен и объемов активов. |
| DeBank | Агрегирует ончейн-данные на лету, но историческую аналитику метрик предоставляет ограниченно. | Показывает ценность выделения аналитики частных рисков (MERC, ENA) в качестве уникального компонента системы. |
| CoinMetrics | Использует гибридную модель: фиксированные ряды цен + расчет коэффициентов под ставку. | Обосновывает необходимость создания отдельного гибкого справочника безрисковых ставок. |

## 4. Предлагаемые требования к первой версии

| Компонент | Предлагаемые функции | Обоснование |
|---|---|---|
| **Аналитический модуль** | Расчет показателей доходности (Шарп, Сортино, FOMO), рисков (VaR через квантили, volatility drag, diversification ratio, ENA, MERC) и ковариаций. | Предоставление пользователю глубокой институциональной оценки портфеля и рисков. |
| **Сервер** | Прием транзакций, валидация данных, ежесуточное создание слепков, синхронизация цен с внешними API и сбор макро-индикаторов. | Централизованная обработка исторических, потоковых и рыночных данных. |
| **Веб-интерфейс** | Список портфелей, вывод последних показателей, матрицы корреляции, тепловые карты рисков и графики макро-рынка. | Удобное визуальное отображение сложных математических метрик в одном месте. |
| **Хранение** | Сохранение времени измерения и времени приема, точная фиксация объемов монет, история транзакций, ежедневные слепки, справочник цен и ставок. | Обеспечение базы для исторических расчетов и исключение ошибок округления для блокчейн-активов. |
| **Рыночный мониторинг** | Сбор внешних метрик капитализации рынка: Open Interest, Fear & Greed index, capital flow, BTC/ETH hashrate. | Оценка общего состояния рынка криптовалют при анализе личного портфеля. |
| **Управление рисками** | Возможность выбора и переключения безрисковой ставки пользователем для пересчета коэффициентов. | Адаптация расчетов под разные варианты (гособлигации США или стейблкоин-стейкинг). |
| **Установка сервера** | Готовые образы, Compose-файл, пример настроек и инструкция. | Самостоятельное развертывание экземпляра сервиса в приватном контуре. |

## 5. Самостоятельное развёртывание

Предлагаемая схема: **внешние крипто-API -> серверное API -> база данных**. Веб-интерфейс получает данные через API.

| Способ установки | Что потребуется от пользователя | Особенности |
|---|---|---|
| Ручная установка | Установить среду выполнения, зависимости, базу данных и настроить запуск планировщика снапшотов. | Позволяет управлять компонентами отдельно, но требует ручной настройки их совместимости. |
| Готовые контейнерные образы | Подготовить контейнерную среду, заполнить настройки в `.env` и запустить Compose. | Минимизирует порог входа, но требует поддержки актуальности образов и порядка обновления. |

В качестве основного метода развёртывания выбраны готовые контейнерные образы. В комплект поставки входят: docker-compose файлы, примеры env-файлов с конфигурацией API-ключей и инструкция для первого запуска.

Серверная часть и модули интеграции с внешними API рассматриваются отдельно. База данных и вычислительный модуль устанавливаются непосредственно в инфраструктуре пользователя.

## 6. Вывод

Для разрабатываемого сервиса будет использоваться гибридный подход с ежедневным логированием состояний активов и цен (подход snapshots для хранения данных и on-the-fly для расчета коэффициентов). Данный выбор позволит без задержек просматривать сложные институциональные показатели доходности и рисков, строить матрицы корреляций и графики изменений через единый веб-интерфейс. При этом использование изолированного справочника безрисковых ставок предоставит инвесторам возможность кастомизировать расчеты под требуемые рыночные условия.

Серверная часть будет доступна в виде готовых контейнерных образов. Развертывание экземпляра сервиса осуществляется с помощью Docker Compose на основе параметров среды, указанных в инструкции к файлу `.env`. Использование готовых образов избавляет конечного пользователя от необходимости ручной сборки математических зависимостей приложения и изолированного поднятия базы данных, обеспечивая при этом полную конфиденциальность транзакций.
